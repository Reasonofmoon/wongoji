# 한국어 첨삭 서비스·기술 리서치

원고지 격자에 교정부호를 오버레이하는 LLM 첨삭 앱을 기획하기 위한 사전 조사.
조사 범위는 (1) 유사 서비스 지형, (2) 활용 가능한 오픈소스·공개 데이터, (3) 라이선스·정책 제약이다.

---

## 1. 유사 서비스 지형

### 1.1 국어 작문 자동 채점·피드백 (직접 경쟁)

| 서비스 | 대상 | 첨삭 방식 | 결과물 형태 |
|---|---|---|---|
| 키위(KEEwi) / 키위티(KEEwiT) — korean.ai | 초중고·대학 글쓰기 수업 | AI 자동 채점 + 항목별 정량 평가(6개 항목), 동료 평가 기능 | 웹 대시보드, 점수·항목별 피드백 |
| 레서(lesser.school) | 초중고 국어 | 비문학 독해 문제 + 글쓰기 AI 첨삭, 시선추적 기반 집중도 분석 | 앱 내 실시간 피드백·성장 분석 |
| 써봄(writegrow.net) | 논술 준비생 | Gemini로 논리구조·근거 타당성·언어 표현 분석 | 웹 리포트 |
| 논술GPT 류 GPT 응용 서비스 | 고3·재수생 | 모범 답안 대비 자기 답안 첨삭 | 채팅 형태 피드백 |

키위는 대학 글쓰기 수업에 실제로 투입되어 효과와 한계가 학술적으로 검토된 유일한 국내 사례다.
두 편의 사례 연구가 공통적으로 보고한 내용은 다음과 같다.

- 긍정: 즉각적·반복적 피드백으로 학습 능률과 수업 흥미가 올라가고, 교수자의 채점 부담이 줄어든다. 문법 영역의 상세 피드백에 대한 학습자 만족도가 높다.
- 한계: 엔진 자체의 오류가 있고, 교수자·튜터가 주는 피드백 수준에는 아직 이르지 못한다. **절대적 평가 지표로 쓸 수 없고 교수자의 최종 평가로 반드시 보완해야 한다.**

→ 기획 반영: 자동 첨삭 결과는 "교사 검토 대기" 상태로 두고, 교사가 항목별로 승인·수정·기각한 뒤에야 학생에게 전달되는 흐름을 기본값으로 둔다.

### 1.2 사람 첨삭 결합형 독서·논술 (오프라인 강점)

| 서비스 | 방식 | 시사점 |
|---|---|---|
| 리딩플러스(AI리딩플러스) | 본사 독서논술 전문 교사가 학생 독서노트·활동지를 직접 첨삭해 5일 내 발송 | 종이 원고에 손으로 첨삭한 결과물을 학부모에게 보내는 것이 여전히 상품 가치. 우리 앱의 산출물이 지향할 형태 |
| 리드인 | 수준별 독서관리 + 총평 첨삭 | 첨삭이 '총평' 단위로 상품화되어 있음 |

사람 첨삭은 회차당 며칠이 걸린다. **결과물의 형태(종이에 교정부호가 얹힌 원고)를 유지하면서 소요 시간을 줄이는 것**이 우리 앱의 자리다.

### 1.3 영어 작문 자동 첨삭 (엔진 설계 참고)

- 파워라이팅: 자체 엔진 WINE으로 문법(Grammar)·어법(Usage)·맞춤법(Mechanics)·구두법(Punctuation) 4영역을 나누어 교정하고, 교사가 개입한 뒤 2차 첨삭을 다시 돌리는 구조.
- Wordvice AI, Paperpal: 학술 영어 교정. 문장 단위 제안 + 대안 문장 제시.

→ 기획 반영: 영역을 나누어 교정하고 **2차 첨삭(재고 후 재검사)을 1급 기능으로 둔다.** 3부의 '재고 요구' 원칙과 맞물린다.

### 1.4 일기·정서 피드백 (인접 시장)

방학일기(AI가 답장해 주는 일기 앱), AI 마음일기(Seamspace, 교사 대시보드·월별 성장 리포트)처럼
첨삭보다 정서적 반응·모니터링에 초점을 둔 앱이 별도 층을 형성하고 있다. 저학년 사용자 확보 경로로 참고할 만하다.

### 1.5 맞춤법 검사기 (도구 층)

부산대학교 인공지능연구실과 (주)나라인포테크의 **한국어 맞춤법/문법 검사기(바른한글)** 는
1991년 개발을 시작해 2001년 웹 서비스를 개시한 사실상의 표준 도구다. 한컴오피스 한글이 2018 버전부터 자체 검사기를 버리고 이 엔진을 도입했고, 잡코리아·사람인 등에 임베드 엔진이 판매되고 있다.

이 검사기의 결과 표시 방식이 우리 기획과 직접 겹친다.

- 오류 단어 위에 대치어를 표시하고, 대치어 색으로 신뢰도를 나타낸다(초록=문맥·규칙 기반 오류, 빨강=오탈자, 보라=띄어쓰기).
- **띄어쓰기·붙여쓰기·문장부호 오류는 교정 부호를 사용해 구분 표시한다.**

즉 "교정부호로 오류를 보여준다"는 발상 자체는 선행 사례가 있다. 다만 표시 대상이 웹 텍스트이고, 원고지 격자·첫머리 서식·문단 들여쓰기 같은 **지면 형식**은 다루지 않는다.

### 1.6 기능 공백 — 우리 앱이 들어갈 자리

1. **원고지 형식 자체를 교정하는 서비스가 없다.** 첫 줄 비우기, 제목 가운데 맞춤, 이름 오른쪽 배치, 문단 첫 칸, 줄 끝 문장부호 매달기 같은 규칙은 어느 검사기도 보지 않는다. 이것은 초·중등 국어 평가에서 실제로 감점 대상이 되는 항목이다.
2. **교정부호를 지면 위에 그려 주는 산출물이 없다.** 기존 서비스의 출력은 점수·항목별 코멘트·인라인 밑줄이다. 교사가 손으로 첨삭한 것과 같은 형태의 인쇄 가능한 원고는 사람 첨삭 서비스만 제공하며, 그것도 며칠이 걸린다.
3. **학생이 다시 고쳐 쓸 수 있는 종이 산출물이 없다.** 첨삭의 마지막 단계는 재고(고쳐 쓰기)인데, 화면 피드백은 그 단계로 이어지지 않는다.

### 2.1 문장부호 소홀 관찰이 곧 아키텍처 근거

KoGEC 연구가 보고한 "대형 LLM은 문장부호 오류에 덜 집중한다"는 관찰은 우리 앱에 그대로 적용된다.
게다가 KAGAS 논문은 한국어 모어 화자가 만든 오류 말뭉치(Kor-Native)에서 **수집된 오류 유형의 대부분이 띄어쓰기였다**고 보고한다.
원고지 첨삭에서 가장 빈번한 오류가 바로 **띄어쓰기와 문장부호, 그리고 지면 형식**이라는 뜻이다.
따라서 전부를 LLM에 맡기지 않는다.

- **규칙 계층(결정적)**: 원고지 형식 검사(첫 칸, 제목 위치, 줄 끝 부호 매달기, 한 칸 한 자), 문장 종결부호 누락, 사전 기반 오탈자 1차 필터. 코드로 판정하므로 재현 가능하고 설명 가능하다.
- **LLM 계층(생성적)**: 겹말·상투어·문체 불일치, 문단 나누기 제안, 주어–서술어 호응, 총평 3단 구조 작성. 판단이 필요하고 정답이 하나가 아닌 층.

이 분리는 비용과 신뢰성에도 유리하다. 형식 오류는 LLM 호출 없이 잡히고, LLM 호출은 내용 층에만 쓴다.

### 2.2 샌드박스 실행 확인

`kiwipiepy` 0.23.2를 전용 환경(`chumsak`)에 설치해 실제로 돌려 보았다. 공유 파이썬 환경에서는 의존성이 고정되어 설치가 거부되므로 전용 환경이 필요하다. 확인 결과는 다음과 같다.

- `space()` — 붙여 쓴 곳을 띄우는 교정은 됐다. `어제나는 친구와같이` → `어제 나는 친구와 같이`. 반면 **잘못 띄운 곳을 붙이지는 못했다**(`놀이 터에서`가 그대로 남았다). 즉 띄움표 후보 탐지에는 쓸 수 있고 붙임표 후보 탐지에는 부족하다.
- `split_into_sents()` — 종결부호가 없어도 문장 경계를 찾아냈다. `비가 왔다 그래서 우리는 뛰어갔다.`를 `비가 왔다` / `그래서 우리는 뛰어갔다.`로 나눈다. **부호 넣음표(마침표 누락) 후보를 규칙 계층에서 결정적으로 잡을 수 있다는 뜻이다.**
- `tokenize()` — 형태소별 원문 시작 위치(`start`, `len`)를 돌려주므로 교정 항목을 원고지 칸 좌표로 옮기는 데 그대로 쓸 수 있다.
- 외부 맞춤법 검사기 웹 엔드포인트는 **의도적으로 호출하지 않았다.** 위 라이선스 조사에서 비상업적 개인 이용으로 한정된 서비스이고, 과거 대량 호출로 운영 피해가 발생한 이력이 있다. 프로토타입은 규칙 계층 + LLM 계층으로만 구성한다.

## 3. 경쟁 구도 정리

기존 서비스는 두 축으로 갈린다.

- **빠르지만 화면에 갇힌 자동 첨삭** — 키위·레서·써봄. 점수와 코멘트는 즉시 나오지만 종이로 이어지지 않는다.
- **종이로 나오지만 느린 사람 첨삭** — 리딩플러스·리드인. 교정부호가 얹힌 원고가 나오지만 며칠이 걸리고 단가가 높다.

우리 앱의 위치는 **"자동 첨삭의 속도 + 사람 첨삭의 산출물"** 이다.
차별 요소는 원고지 격자를 1급 데이터 구조로 다룬다는 점 하나로 요약된다.
칸 좌표가 있으면 교정부호를 정확한 위치에 그릴 수 있고, 그것이 곧 인쇄 가능한 첨삭본이 된다.

## 4. 위험과 대응

| 위험 | 대응 |
|---|---|
| LLM 오판(맞는 표현을 틀렸다고 지적) | 되살림표 흐름을 UI에 그대로 구현. 교사·학생이 항목 단위로 기각할 수 있게 하고, 기각 이력을 프롬프트 개선에 사용 |
| 자동 첨삭을 최종 평가로 오용 | 선행 연구의 결론을 그대로 반영해 '교사 검토 대기' 기본값. 점수를 전면에 두지 않고 교정 항목과 총평을 전면에 둔다 |
| 과잉 첨삭 | 초점 첨삭을 기본 모드로. 교사가 이번 회차의 초점 항목을 2개까지 선택하면 그 외 항목은 집계만 하고 지면에는 그리지 않는다 |
| 학생 글의 개인정보 | 원문 저장 최소화, 보호자 동의 절차, 보관 기간 설정. 학교 도입 시 필수 |
