# 원고지 첨삭 앱 기획서

작업명 **원고지 첨삭기**. 학생 글을 받아 **원고지 격자 위에 교정부호가 얹힌 첨삭본**을 만들고,
교사가 검토·승인한 뒤 학생에게 돌려주는 도구.
리서치 결과(`리서치_한국어첨삭_시장과자원.md`)와 동작하는 프로토타입(`chumsak_app.py`)을 근거로 작성했다.

---

## 1. 문제와 한 줄 정의

기존 자동 첨삭은 빠르지만 화면에 갇혀 있고, 사람 첨삭은 종이로 나오지만 며칠이 걸린다.
**원고지 첨삭기는 자동 첨삭의 속도로 사람 첨삭의 산출물을 만든다.**

차별 요소는 하나로 요약된다. 원고지 격자를 1급 데이터 구조로 다룬다.
칸 좌표가 있으면 부호를 정확한 자리에 그릴 수 있고, 그것이 곧 인쇄해서 다시 고쳐 쓸 수 있는 종이가 된다.
조사한 어느 서비스도 지면 형식(첫 칸·제목 위치·줄 끝 부호 매달기)을 교정 대상으로 보지 않는다.

## 2. 사용자와 맥락

| 사용자 | 맥락 | 필요한 것 |
|---|---|---|
| 초·중등 국어 교사 | 30명 학급의 주간 글쓰기. 한 편에 5분 이상 쓸 수 없다 | 초안 첨삭을 자동으로 받고 손으로 고쳐 승인 |
| 독서·논술 학원 강사 | 회차마다 첨삭본을 학부모에게 보낸다 | 인쇄 가능한 첨삭본, 회차별 누적 기록 |
| 학생(고학년 이상) | 제출 전 스스로 점검 | 자기 첨삭 모드. 정답을 주지 않는 간접 첨삭 |
| 학부모 | 아이 글의 변화를 보고 싶다 | 첨삭본 PDF와 회차 비교 |

주 사용자는 **교사**다. 학생 직접 사용은 간접 첨삭 모드로 제한한다. 이유는 4.2절.

## 3. 핵심 기능과 제외 기능

**핵심 기능**

1. 원고 입력 — 타이핑, 붙여넣기, 원고지 사진 업로드(2단계).
2. 원고지 배치 — 200자/400자 격자에 표기 규칙대로 앉히기. 지면 형식 오류 검출.
3. 자동 첨삭 — 규칙 계층 + LLM 계층. 초점 첨삭(부호 2종 지정)과 항목 수 상한.
4. 교사 검토 — 항목별 승인·수정·기각. 기각은 되살림표로 지면에 남긴다.
5. 첨삭본 출력 — PNG/PDF. 교정 목록과 총평 3단이 한 장에 들어간다.
6. 재고 접수 — 학생이 고쳐 쓴 원고를 다시 받아 2차 첨삭. 회차 비교.

**의도적으로 넣지 않는 것**

- **점수·등급 자동 부여.** 선행 연구가 자동 채점을 절대 지표로 쓸 수 없다고 결론했다. 점수를 넣으면 교사 검토 단계가 형식이 된다.
- **글 대신 써 주기.** 문장 통째 교체 제안은 검증 게이트가 반려한다(5.2절).
- **실시간 타이핑 교정.** 초고를 끝까지 쓰게 하는 것이 첨삭 지도의 전제다.

## 4. 파이프라인 아키텍처

```
원문 ─┬─▶ 규칙 계층 (결정적)                     ┐
      │    · 띄어쓰기 후보      kiwipiepy space() │
      │    · 종결부호 누락      split_into_sents()│
      │    · 문단 첫 칸·지면 형식                 ├─▶ 정규화 ─▶ 검증 게이트 ─▶ 초점 필터
      └─▶ LLM 계층 (생성적)                       │                              │
           · 겹말·상투어·문체·호응                │                              ▼
           · 문단 나누기 / 총평 3단               ┘                    원고지 오버레이 렌더러
                                                                                │
                                                        교사 검토(승인·수정·기각) ─▶ PNG/PDF
```

### 4.1 왜 두 계층으로 나누는가

KoGEC 연구는 파인튜닝 모델이 오류 유형 전반에 고르게 대응한 반면 **대형 LLM은 문장부호 오류에 상대적으로 소홀했다**고 보고했다.
원고지 첨삭에서 가장 빈번한 오류가 바로 띄어쓰기·문장부호·지면 형식이다. 그래서 그 층은 LLM에 맡기지 않는다.

프로토타입 실측이 이 설계를 뒷받침한다. 예시 두 편에서 **지면에 그려진 11건 중 8건이 규칙 계층**에서 나왔다.
LLM이 낸 11건 중 지면에 남은 것은 3건 — 겹말(뺌표 2건)과 문단 나누기(줄 바꿈표 1건)뿐이었고, 나머지 8건은 게이트가 반려했다.
즉 LLM 계층은 판단이 필요한 항목만 담당하고, 형식 오류는 규칙 계층이 결정적으로 처리한다.
비용 측면에서도 형식 오류는 LLM 호출 없이 잡히므로 원고 한 편당 LLM 호출은 1회로 끝난다.

### 4.2 교사 승인을 기본값으로 두는 이유

키위(KEEwi)를 대학 글쓰기 수업에 투입한 두 편의 사례 연구는 공통적으로
자동 피드백이 교수자 수준에 이르지 못하며 **최종 평가는 교수자가 반드시 보완해야 한다**고 결론했다.
따라서 자동 첨삭 결과의 기본 상태는 `검토 대기`이며, 교사 승인 없이 학생에게 노출되지 않는다.
학생 직접 사용은 정답을 주지 않는 간접 첨삭 모드로 제한한다.

## 5. 검증 게이트 — 이 앱의 핵심 자산

LLM은 부호를 잘못 고르고, 없는 오류를 만들고, 한 문장을 통째로 바꾸라고 한다.
**게이트는 프로토타입에서 실제로 그 세 가지를 모두 잡았다.**

### 5.1 정규화 (부호 관례에 맞게 고침)

| 입력 | 교정 | 근거 |
|---|---|---|
| `replace` 인데 띄어쓰기만 다름 | `join`(붙임표)으로 변환 | 붙여쓰기 교정은 고침표가 아니다 |
| `insert` 인데 넣을 것이 문장부호 | `punct`(부호 넣음표)로 변환 | 부호 넣음표가 별도로 있다 |
| 이미 그 부호가 있는 자리에 또 넣기 | 항목 폐기 | LLM 헛짚음 |

### 5.2 반려 규칙

| 규칙 | 이유 |
|---|---|
| target을 본문에서 찾지 못함 | 부호를 그릴 자리가 없다 |
| span 부호의 범위가 12자 초과 | 지면에서 읽을 수 없는 부호가 된다 |
| 고침표의 원문 또는 대체문이 8자 초과 | 문장 통째 교체는 부호가 아니라 총평에 쓸 내용이다 |
| 넣음표·부호 넣음표의 삽입 문자가 4자 초과 | 칸에 들어가지 않는다 |
| 사유(reason)가 비어 있음 | 학생에게 설명할 수 없는 지적은 첨삭이 아니다 |
| 규칙 계층 항목과 자리가 겹침 | 같은 자리에 부호 두 개를 그릴 수 없다. 결정적 계층이 우선 |
| 되살림표·줄 이음표·끌어 올림/내림표·내어쓰기표 사용 | 교사가 지면을 편집할 때 쓰는 부호다. 자동 첨삭에서 금지 |

### 5.3 실측 결과

예시 두 편(초등 생활문, 중등 주장하는 글)에서 게이트가 반려한 8건의 사유 분포:

| 사유 | 건수 |
|---|---|
| 규칙 계층과 자리 겹침 (띄움표 2, 부호 넣음표 1) | 3 |
| 문장 통째 교체 | 2 |
| 부호 범위 과대 | 1 |
| 삽입 문자 길이 초과(43자를 넣으려 함) | 1 |
| 교사 전용 부호(되살림표) 사용 | 1 |

부호를 그린 11건의 칸 좌표는 모두 실제 오류 위치와 일치했다(`unresolved` 0건).
같은 원고를 다시 돌리면 LLM 계층의 항목 구성이 달라진다. 게이트는 매번 통과 항목을 다시 판정하므로
**출력의 품질은 유지되지만 항목 목록은 재현되지 않는다.** 운영에서는 온도를 낮추고 회차별 결과를 저장해 비교한다.

## 6. 데이터 스키마

교정 항목 하나가 데이터 모델의 중심이다. 지면 좌표를 저장하지 않고 **문자열 앵커**로 저장한다.
원고가 수정되어 칸 배치가 바뀌어도 앵커는 살아남는다.

```jsonc
// correction
{
  "id": "c_012",
  "kind": "punct",              // 14개 교정부호 중 하나
  "anchor": {"target": "왔다", "nth": 0},   // 본문에서 복사한 문자열 + 몇 번째 출현
  "text": ".",                  // 넣거나 고칠 글자 (넣음표·부호 넣음표·고침표만)
  "reason": "문장이 끝났는데 마침표가 없다",
  "layer": "표기",              // 표기 | 내용
  "severity": "높음",
  "source": "rule",             // rule | llm | teacher
  "state": "approved",          // pending | approved | edited | rejected
  "gate": null                  // 반려 시 사유 문자열
}
```

```jsonc
// submission
{
  "id": "s_2026_0312_kim",
  "student": {"id": "u_31", "grade": "초6"},        // 이름은 별도 테이블
  "round": 1,                                       // 재고 회차
  "parent_submission": null,
  "text": "어제 나는 ...",
  "sheet": {"ncols": 20, "nrows": 10, "double_space": true},
  "focus": ["space", "punct"],                      // 이번 회차 초점 부호
  "corrections": ["c_012", "..."],
  "review": {"good": "...", "fix": "...", "next": "..."},
  "state": "teacher_review",   // draft | auto_done | teacher_review | returned | revised
  "artifacts": {"png": "...", "pdf": "..."}
}
```

교사 행위는 `correction.state` 변경과 감사 로그로 남긴다. 기각된 항목은 삭제하지 않고
`state: rejected`로 두어 **되살림표로 지면에 표시**한다. 학생은 교사가 무엇을 되살렸는지 본다.
기각 이력은 프롬프트·게이트 개선의 유일한 학습 신호다.

## 7. 화면 흐름

1. **원고 입력** — 텍스트 입력 또는 사진 업로드. 학년·글 종류 선택.
2. **원고지 미리보기** — 칸에 앉힌 결과. 이 단계에서 지면 형식 오류를 먼저 보여준다(LLM 호출 전).
3. **초점 선택** — 이번 회차에 볼 항목 2개까지. 기본값은 학년별 권장 초점.
4. **자동 첨삭 결과** — 부호가 얹힌 원고지 + 교정 목록. 반려된 항목은 접힌 영역에 사유와 함께 표시(교사만).
5. **교사 검토** — 항목별 승인/수정/기각. 총평 3단은 수정 가능한 텍스트.
6. **출력** — PNG/PDF. 학생용(정답 포함)과 간접 첨삭용(정답 □로 가림) 두 판본.
7. **재고 접수** — 고쳐 쓴 원고 입력 → 2차 첨삭. 1차와 나란히 비교.

4단계에서 **반려 항목을 교사에게만 보여주는 것**이 중요하다. 게이트가 왜 반려했는지 교사가 확인할 수 있어야 하고,
동시에 학생이 걸러진 지적을 볼 필요는 없다.

## 8. 입력 경로

| 경로 | 방식 | 단계 |
|---|---|---|
| 타이핑·붙여넣기 | 그대로 처리 | 1단계 |
| 원고지 사진 | 격자 검출 → 칸 분할 → 칸별 인식 → 원문 복원 | 2단계 |
| 파일(hwp/docx/txt) | 텍스트 추출 | 2단계 |

사진 경로는 칸이 이미 있으므로 일반 손글씨 OCR보다 유리하다. 격자를 검출하면 문자 분할 문제가 사라지고
칸 단위 단일 글자 인식으로 환원된다. 학습·평가 데이터는 AI-Hub의 한글 글자체(인쇄체+손글씨)와 손글씨 OCR 데이터를 쓴다(가입·승인 필요).
다만 **인식 오류가 첨삭 오류로 번지므로**, 사진 경로에서는 복원된 텍스트를 교사가 확인하는 단계를 반드시 넣는다.

## 9. 기술 스택과 라이선스 경계

| 계층 | 선택 | 근거 |
|---|---|---|
| 형태소·문장 분리 | kiwipiepy | pip 설치, 실측 확인. `space()`는 띄움표 후보, `split_into_sents()`는 종결부호 누락 탐지 |
| 사전 기반 오탈자 | hunspell-dict-ko | 상업 배포가 명시적으로 가능한 유일한 오픈 사전(3중 라이선스 + 사전 데이터 CC BY-SA 4.0) |
| 내용·표현 첨삭 | 상용 LLM API (구조화 출력) | 판단이 필요한 층. 도구 스키마로 출력 형식을 고정 |
| 렌더링 | 자체 원고지 렌더러 | `wongoji-chumsak` 스킬로 분리해 두었다 |

**쓰지 않는 것**: 네이버·다음 검사기 래퍼(py-hanspell 등)와 부산대 검사기 크롤링.
전자는 결과의 저작권·책임이 해당 회사에 있고, 후자는 비상업적 개인 이용으로 한정되며 과거 대량 호출로 운영 피해가 발생한 이력이 있다.
상용화 시 부산대·나라인포테크의 정식 임베드 엔진 라이선스 구매를 검토한다.

## 10. 로드맵

**1단계 — 교사용 웹 (프로토타입 완료분 + UI)**
텍스트 입력, 규칙+LLM 첨삭, 게이트, 교사 검토, PNG/PDF 출력. 한 학급 단위 시범 운영.
검증 목표: 교사가 첨삭 한 편에 쓰는 시간, 게이트 반려율, 교사 수정률.

**2단계 — 회차 관리와 사진 입력**
재고 접수·회차 비교, 학급 대시보드, 원고지 사진 인식(교사 확인 단계 포함), 학부모용 PDF 발송.

**3단계 — 학습 신호 반영**
교사 기각 이력으로 프롬프트·게이트 규칙 개선. 학년별 초점 자동 추천. 오류 유형 통계 리포트.
KAGAS의 14개 오류 유형 체계에 맞춰 라벨을 정리하면 공개 평가셋(K-NCT, KoLLA v2.0)으로 성능을 측정할 수 있다.

## 11. 평가 지표

| 지표 | 정의 | 프로토타입 값 |
|---|---|---|
| 부호 위치 정확도 | 그린 부호 중 의도한 칸에 앉은 비율 | 11/11 (`unresolved` 0) |
| 게이트 반려율 | LLM이 낸 항목 중 반려된 비율 | 8/11 (LLM 11건 중 3건만 지면에) |
| 규칙 계층 기여율 | 지면 부호 중 규칙 계층 출처 비율 | 8/11 |
| 교사 수정률 | 교사가 수정·기각한 항목 비율 | 미측정 (1단계 시범 운영에서) |
| 재고 제출률 | 첨삭본을 받고 고쳐 쓴 원고를 낸 비율 | 미측정. 첨삭의 실질적 성과 지표 |

교사 수정률과 재고 제출률이 이 앱의 성패를 가른다.
전자가 높으면 자동 첨삭이 일을 줄여 주지 못한 것이고, 후자가 낮으면 첨삭이 학습으로 이어지지 않은 것이다.

## 12. 위험과 대응

| 위험 | 대응 |
|---|---|
| LLM이 맞는 표현을 틀렸다고 지적 | 항목별 기각 + 되살림표. 기각 이력을 개선 신호로 |
| 자동 첨삭을 최종 평가로 오용 | 점수 기능 없음. 교사 승인 없이는 학생에게 노출되지 않음 |
| 과잉 첨삭 | 초점 첨삭 기본값, 항목 수 상한, 반려 항목은 교사에게만 |
| 출력 비재현성 | 온도 하향, 회차별 결과 저장, 규칙 계층 비중 유지 |
| 학생 글의 개인정보 | 원문 보관 기간 설정, 보호자 동의, 이름과 원고 분리 저장 |
| 사진 인식 오류의 전파 | 복원 텍스트 교사 확인 단계 필수 |
| 외부 검사기 의존 | 규칙 계층은 오픈 라이선스 자원과 자체 코드로만 |
