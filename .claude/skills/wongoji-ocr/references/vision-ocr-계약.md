## 왜 전통 OCR이 아니라 비전 모델인가

Tesseract 계열은 인쇄체 라틴 문자에 맞춰져 있고 한글 손글씨에서 무너진다. 원고지는
더 어렵다 — 칸 격자선이 문자와 겹치고, 학생 글씨는 칸을 넘나들며, 교정부호가 이미
그려져 있을 수도 있다.

비전 LLM(Gemini `inlineData`, Claude vision)은 이미지 한 장을 통째로 읽고 레이아웃을
함께 이해한다. 격자와 손글씨를 구분하라고 **말로 지시할 수 있다.** 전통 OCR에는 그
지시 통로가 없다.

대가는 두 가지다. **모델이 "친절하게" 텍스트를 고칠 수 있고**, 같은 이미지에 매번
다른 답을 낼 수 있다. 아래 규약은 대부분 이 두 가지를 막기 위한 것이다.

## 참조 구현에서 가져온 것과 뒤집은 것

참조: `github.com/kukbapman/ocr` — 영어 시험지 OCR + 출처 매칭. Node/Express + Gemini.

**LICENSE 파일이 없다. 코드를 복사하지 않는다.** 접근 방식만 참조하고 FastAPI로
직접 구현한다. 런타임을 Node로 늘리면 v1 모놀리스 원칙도 깨진다.

| 참조 구현 | 우리 |
|-----------|------|
| `inlineData: {mimeType, data: base64}` + 강한 systemInstruction | **그대로 가져온다.** 검증된 호출 형태다 |
| "ABSOLUTE VERBATIM (NO AI INFERENCE)" 규칙 | **그대로, 더 강하게.** 우리에겐 훨씬 치명적이다 |
| 파일명 자연 정렬로 페이지 순서 보장 | 그대로 |
| `blocks: [{id, page, type, status, text}]` 구조화 반환 | 칸 정보를 얹어 확장 |
| PDF를 페이지별로 쪼개 각각 전송 | 그대로 |
| **"IGNORE ALL HANDWRITING"** | **정반대로 뒤집는다.** 아래 참조 |
| `safetySettings: BLOCK_NONE` | 쓰지 않는다. 학생 글에 필요 없다 |
| 저작권 경고를 무시하라는 지시 | 옮기지 않는다 |

**손글씨/인쇄 역전이 가장 중요한 차이다.** 참조 구현은 인쇄된 시험지 본문을 뽑고
학생이 쓴 답을 버린다. 우리는 정확히 반대다 — **인쇄된 격자선·머리글·쪽번호를 버리고
학생 손글씨만 취한다.** 프롬프트를 그대로 베끼면 빈 출력이 나온다.

## 응답 스키마

OCR 출력은 **plain text가 아니다.** 텍스트만 뽑으면 이 앱이 필요로 하는 정보가
소실된다. 문단 첫 칸을 비웠는지(O8), 부호를 어느 칸에 매달았는지가 원문 정보다.

```json
{
  "ocr_id": "529803ca238a",
  "ncols": 20,
  "pages": [
    {"page": 1, "ncols": 20, "rows": [
      {"row": 1, "cells": "동생가 아이스크림를 먹었다 ", "conf": 0.95, "uncertain": []},
      {"row": 2, "cells": " 나도 먹고 싶어서 엄마한 ", "conf": 0.62, "uncertain": [4, 5]}
    ]}
  ],
  "low_conf": [{"page": 1, "row": 2, "col": 4, "ch": "", "conf": 0.0, "why": "읽지 못한 칸"}],
  "warnings": ["1쪽: 격자를 넘어 쓴 글자"],
  "confirmed": false
}
```

**칸은 고정폭 문자열로 주고받는다.** `cells`는 정확히 `ncols` 글자이고 **빈 칸은 공백
한 자**다. 칸마다 객체를 만들면 한 장에 400개가 되어 토큰이 낭비되고, 모델이 칸을
빠뜨리기 쉽다. 고정폭 문자열은 문자 위치가 곧 칸 번호라 어긋날 여지가 없다.

| 필드 | 뜻 |
|------|-----|
| `cells` | 정확히 `ncols` 글자. **빈 칸은 공백. 빼고 붙이지 않는다** |
| `conf` | 0~1. 행 단위 확신도 |
| `uncertain` | 읽지 못한 칸 번호(1부터). 추측으로 채우는 대신 여기 넣는다 |
| `low_conf` | 교사 확인 화면이 먼저 짚을 자리 |

**`text`가 이 응답에 없는 것이 게이트다.** 본문은 `/api/ocr/confirm`이 교사가 고친
칸을 받은 뒤에만 준다. 확인을 건너뛰면 OCR 오인식이 학생 오류로 첨삭되는데, 그 구분은
기계가 할 수 없다. 응답에 본문을 넣어 두면 그 게이트가 관례가 되고, 관례는 지켜지지
않는다.

**빈 칸을 버리지 않는 이유:** 공백을 빼고 글자만 이으면 문단 첫 칸 비움이 사라진다.
그러면 O8(원고지 형식) 오류를 영원히 못 잡는다.

## 엔드포인트

| 경로 | 하는 일 |
|------|--------|
| `POST /api/ocr` (multipart `files`) | 사진 -> 칸 격자. **본문 텍스트를 주지 않는다** |
| `POST /api/ocr/confirm` `{ocr_id, pages}` | 교사가 고친 칸 -> 본문 확정. 여기서만 `text`가 나온다 |
| `POST /api/chumsak` `{ocr_id}` | `confirmed`가 아니면 409. 클라이언트가 보낸 `text`는 버리고 확정 본문을 쓴다 |

**본문 재구성 규칙:** 행 끝의 남는 공백은 잘라 내고, 행을 그대로 이어 붙인다. **첫
칸이 빈 행 앞에서만 `\n`을 넣는다.** 원고지에서 이어지는 행은 첫 칸부터 채우므로
(띄어쓰기가 행 끝에 걸리면 앞 행 끝에 붙인다), 첫 칸이 비었다는 것은 문단 시작을
뜻한다. 완전히 빈 행은 건너뛴다.

## 프롬프트 규약

시스템 지시에 반드시 넣는다.

1. **절대 원문 그대로.** 맞춤법·띄어쓰기·문장부호를 **고치지 마라.** 학생이 `학교은`
   이라고 썼으면 `학교은`으로 낸다. 이것이 가장 중요한 규칙이다
2. **손글씨만.** 인쇄된 원고지 격자선, 머리글(제목·이름·날짜 칸의 인쇄 문구), 쪽번호는
   무시한다. 학생이 손으로 쓴 것만 낸다
3. **칸 단위로.** 한 칸에 한 글자. 빈 칸은 빈 문자열로 남긴다. 숫자·로마자 소문자만
   한 칸에 두 자가 올 수 있다
4. **읽을 수 없으면 비운다.** 추측해서 채우지 마라. `conf`를 낮게 주고 `ch`를 비운다
5. **이미 그려진 교정부호는 글자가 아니다.** 빨간 부호가 보이면 `warnings`에 적고
   `ch`에는 넣지 않는다
6. 구조화 출력(tool_use / responseSchema)만 신뢰한다. 본문 텍스트 JSON은 파싱하지 않는다

### 규칙 1을 강조하는 이유

일반 OCR에서 자동 교정은 기능이다. **첨삭기에서는 데이터 파괴다.** 모델이 `학교은`을
`학교는`으로 고쳐 주면 첨삭할 오류 자체가 사라지고, 앱은 "오류가 없습니다"라고 답한다.
사용자가 겪는 증상은 "맞춤법을 못 잡는다"인데 원인은 규칙 계층이 아니라 OCR이다.

이 실패는 조용해서 더 나쁘다. 규칙을 아무리 고쳐도 점수가 안 오른다.

## 신뢰도와 교사 확인

**OCR 결과를 곧바로 첨삭 파이프라인에 넣지 않는다.** 교사 확인 화면을 반드시 거친다.

이유: `학교은`이 학생이 쓴 오류인지 OCR이 `는`을 `은`으로 잘못 읽은 것인지 **기계는
구분할 수 없다.** 확인 없이 첨삭하면 앱이 OCR 오인식을 학생 오류로 지적한다. 학생은
자기가 맞게 쓴 글자를 틀렸다고 배운다. 이 앱에서 가능한 최악의 실패다.

확인 화면의 최소 요건:
- 원본 이미지와 칸 격자를 나란히 놓는다
- `conf`가 임계값(기본 0.85) 미만인 칸을 표시한다
- 칸 단위로 고칠 수 있다. 통짜 textarea로 되돌리면 칸 정보가 깨진다
- 교사가 **확인 완료**를 눌러야 첨삭이 돈다

## 페이지·다중 파일 처리

- 여러 장을 올릴 수 있게 한다. 원고지는 원래 여러 장이다
- 파일명 자연 정렬(1, 2, 10)로 순서를 정한다. 사전순으로 정렬하면 10이 2 앞에 온다
- PDF는 페이지별로 쪼개 각각 보낸다. 한 번에 넣으면 페이지 경계가 뭉개진다
- 페이지가 넘어가도 `text`는 하나로 이어진다. 문단이 페이지를 가로지를 수 있다

## 개인정보

학생 손글씨 사진은 개인정보다.

- 업로드 이미지는 세션에 영구 보관하지 않는다. 첨삭이 끝나면 지운다
- 보관해야 하면 보관 기간과 보호자 동의 절차를 먼저 정한다 (기획서 12장)
- 이미지를 외부 모델에 보내는 것 자체가 제3자 전송이다. 교사에게 명시한다
- 골드 코퍼스에 실제 학생 이미지를 넣을 때는 이름·학교·지명을 가린다
