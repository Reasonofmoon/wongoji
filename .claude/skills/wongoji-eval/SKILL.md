# 정확도 평가

이 앱이 "불완전하다"는 말을 숫자로 바꾸는 층이다. 지금 `tests/`에 있는 것은
레이아웃·게이트·계약 픽스처, 즉 **배관 검사**다. 부호가 올바른 칸에 앉는지는 보지만
**맞아야 할 오류를 잡았는지는 아무도 보지 않는다.** 그래서 QA 리포트가 "실패 없음"
인데 사용자는 "다 못 찾는다"고 한다. 둘 다 사실이다.

측정 없이 규칙을 고치면 개선인지 퇴행인지 모른다. **규칙보다 코퍼스가 먼저다.**

스키마·생성 절차·분포 목표는 `references/corpus-schema.md`를 읽는다.
오류 유형 코드는 `wongoji-orthography`의 카탈로그가 단일 출처다.

**기존 실측 말뭉치의 분포를 코퍼스 목표로 베끼지 않는다.** 그 796건은 개발 문서·
README에서 나왔고, 학생 글에 흔한 조사 누락·마침표 없이 이어지는 문장·구어체 혼용이
거의 없다. 규칙 **우선순위**의 근거로는 쓰되(`wongoji-orthography/references/말뭉치_근거.md`),
**분포 목표**는 학년·갈래 기준으로 따로 잡는다.

## 구성

```
tests/corpus/
├── el.jsonl          초등 (합성)
├── ms.jsonl          중등 (합성)
├── negative.jsonl    오탐 억제 전용 (오류 없는 글 + 함정)
├── holdout.jsonl     실제 학생 글 (source: real, 튜닝 금지)
└── _baseline.json    직전 유형별 F1. 퇴행 판정 기준
```

## 두 스크립트

**코퍼스를 손대면 먼저 검증한다.** span이 한 칸 밀리면 평가 전체가 조용히 틀린다.

```bash
python .claude/skills/wongoji-eval/scripts/validate_corpus.py tests/corpus
```

**그다음 측정한다.**

```bash
python .claude/skills/wongoji-eval/scripts/eval_accuracy.py
python .claude/skills/wongoji-eval/scripts/eval_accuracy.py --llm        # LLM 계층 포함
python .claude/skills/wongoji-eval/scripts/eval_accuracy.py --held       # 보류항목도 인정
python .claude/skills/wongoji-eval/scripts/eval_accuracy.py --update-baseline
```

`--llm` 없이 도는 것이 기본이다. 규칙 계층은 결정적이라 같은 수를 두 번 내지만,
LLM은 매번 달라 회귀 판정에 쓸 수 없다. **규칙 계층 점수가 이 하네스의 게이트다.**
LLM 포함 측정은 참고 지표로만 본다.

`--held`는 진단용이다. 기본 점수와 `--held` 점수의 차이가 크면 **엔진은 찾았는데
지면 상한이 잘라낸 것**이다. 이때 고칠 곳은 규칙이 아니라 `focus_filter`다.

## 판정 기준

| 지표 | 뜻 | 낮을 때의 증상 |
|------|-----|--------------|
| 재현율 | 진짜 오류 중 잡은 비율 | "틀린 데를 다 못 찾는다" |
| 정밀도 | 잡은 것 중 진짜인 비율 | "멀쩡한 데를 고치라고 한다" |
| 음성 위반 | 잡으면 안 되는 자리에 부호 | 교사가 앱을 버리는 가장 빠른 길 |

매칭은 구간 겹침으로 한다. 경계 부호(띄움·넣음·부호넣음·줄바꿈·줄이음)는 ±1칸을
같은 자리로 본다. 부호가 앉는 칸은 하나지만 사람이 span을 적을 때 한 칸 흔들린다.

## 게이트

| 게이트 | 조건 | 실패 시 |
|--------|------|--------|
| 유형별 퇴행 | 어떤 유형의 F1이 기준선보다 0.01 넘게 하락 | 즉시 FAIL. 규칙을 되돌리거나 조건을 조인다 |
| 음성 픽스처 | 위반 1건 이상 | 즉시 FAIL. 재현율을 포기하더라도 막는다 |
| 전체 F1 | `--gate` 값 미만 | 출시 게이트 FAIL |

**기준선은 개선한 뒤에만 올린다.** 점수가 떨어졌는데 `--update-baseline`으로
덮으면 게이트가 무의미해진다. 퇴행을 통과시키려면 사용자에게 이유를 보고하고
승인을 받는다.

## 개선 루프

```
1. 목표 유형 선택            ← 재현율이 가장 낮은 유형부터
2. 그 유형의 양성·음성 예문 추가
3. validate_corpus.py
4. eval_accuracy.py          ← 기준선 확인 (보통 재현율 0)
5. 규칙 구현                  ← wongoji-orthography
6. eval_accuracy.py          ← 목표 유형 ↑, 다른 유형 유지 확인
7. 다른 유형이 떨어졌으면 6으로. 규칙을 지우지 말고 오탐 조건을 붙인다
8. --update-baseline
```

한 번에 한 유형만 손댄다. 두 규칙을 같이 올리면 어느 쪽이 오탐을 냈는지 못 가린다.

## 코퍼스를 만들 때 자주 나오는 실패

**글을 다 쓰고 오류를 찾아 표시한다.** 반드시 어긋난다. 깨끗한 글을 먼저 쓰고
오류를 하나씩 주입하면서 그 자리를 기록한다.

**span을 눈으로 센다.** `text.index()`로 계산한다. 검증기의 `target` 대조가 이걸
잡지만, 애초에 계산해서 넣는 것이 빠르다.

**한 유형만 든 글을 만든다.** 실제 학생 글은 유형이 섞여 있고, 섞였을 때만 겹침
처리와 상한이 드러난다. 한 편에 3~6유형을 섞는다.

**오류만 넣고 negatives를 안 넣는다.** 그러면 정밀도가 항상 1.0으로 보인다. 모든
자리에 부호를 다는 엔진이 만점을 받는다.

**실제 학생 글을 보면서 규칙을 고친다.** 홀드아웃이 오염된다. 실제 글은 마지막에
한 번만 돌린다.

## OCR 게이트는 따로 잰다

사진 입력이 들어오면서 정확도가 두 갈래가 됐다. **섞으면 원인을 못 가린다.**

| 지표 | 무엇 | 누가 고치나 |
|------|------|------------|
| 첨삭 F1 | 유형별 정밀도·재현율 | orthography-lead |
| CER | 문자 오류율 | ocr-dev |
| 칸 정렬 정확도 | 글자가 올바른 (행, 칸)에 놓인 비율 | ocr-dev |
| **교정 침묵률** | OCR이 학생 오류를 고치지 않고 그대로 낸 비율 | ocr-dev |

**첨삭 정확도 평가는 항상 텍스트 입력으로 돈다.** OCR을 끼워 재면 F1이 떨어졌을 때
규칙 탓인지 인식 탓인지 못 가리고, orthography-lead가 멀쩡한 규칙을 헛되이 고친다.

**교정 침묵률이 이 앱 고유의 지표다.** 재는 법: 골드 코퍼스의 오류 문장을 원고지에
옮겨 쓴 이미지를 넣고, OCR 출력에 그 오류가 **그대로 남아 있는지** 본다. 사라졌으면
OCR이 고친 것이다. 침묵률이 낮으면 규칙을 아무리 고쳐도 점수가 오르지 않는다 —
원인이 입구에 있기 때문이다. 첨삭 F1을 진단하기 전에 이것부터 본다.

침묵률 측정용 이미지는 `tests/corpus/ocr/`에 두고, 원본 텍스트를 정답으로 삼는다.
실제 학생 손글씨를 쓸 때는 이름·학교·지명을 가린다.
